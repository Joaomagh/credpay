# PostgreSQL Alpine candidate — evaluation only

This directory does not replace the active PostgreSQL image or migrate any data.
The base is the [Docker Official Image `postgres:17.12-alpine3.24`](https://hub.docker.com/_/postgres/tags?name=17.12-alpine3.24), pinned to index digest `sha256:a77aa70e641402a21411b92b721c58d10f23b50ae5fdd2333efd22d166e1e5f7` (AMD64 manifest `005c5c37…`, ARM64 manifest `93f3c32b…`, checked 16 November 2026). This remains PostgreSQL major 17 and Alpine 3.24.

The official [entrypoint](https://github.com/docker-library/postgres/blob/master/docker-entrypoint.sh) calls `gosu postgres` when started as root. The candidate installs Alpine main's [`su-exec` 0.3-r0](https://pkgs.alpinelinux.org/packages?branch=v3.24&name=su-exec) (MIT, C implementation) and keeps the entrypoint interface through a symlink for an explicit root start. The first CI run proved initialization and restart, but the scanner still found the original `gosu` in the inherited image layer. The final stage copies the prepared filesystem into a fresh image layer and restores the runtime metadata from the [official Dockerfile](https://github.com/docker-library/postgres/blob/master/17/alpine3.24/Dockerfile). It sets `USER postgres` as the default; the probe must prove the image metadata, runtime UID, fresh-volume initialization and restart before crediting this change. This is a focused dependency change, not a security waiver. The build still depends on Alpine's package repository; the resolved package and image IDs are checked in native CI. The parent image, package mirror and CI runner remain in the trust base.

`postgres-candidate.yml` builds natively on AMD64 and ARM64, verifies the non-root default and the explicit root-start fallback, initializes a database, writes a row, restarts against its **own** labeled volume, and checks the row. The CI job then scans the saved image with pinned Trivy 0.75.0 and an empty ignore file. `report_candidate.py` projects package names, versions and every vulnerability ID/severity without publishing image environment. Missing OS coverage, wrong architecture, a missing `su-exec` package or a remaining `gosu` Go binary fail the job. CRITICAL/HIGH findings also fail it after selected evidence is saved and uploaded; lower severities remain visible. A green job does not approve the image.

The 21 November selected inventories identified `CVE-2026-86144` in inherited `libxml2` 2.13.9-r2 (HIGH; fixed 2.13.9-r3), plus three MEDIUM and two LOW IDs in inherited `libcrypto3`/`libssl3` 3.5.9-r0 (fixed 3.5.9-r1). The [Alpine 3.24 package index for libxml2](https://pkgs.alpinelinux.org/packages?arch=x86_64&branch=v3.24&name=libxml2) and [OpenSSL](https://pkgs.alpinelinux.org/packages?arch=x86_64&branch=v3.24&name=openssl&repo=main) showed the fixed revisions on x86_64. The candidate pins these revisions during the prepared stage; both native architecture builds and fresh scans must confirm availability and resulting inventory. The active database image is unchanged.

[CI run 44026136151](https://github.com/Joaomagh/credpay/actions/runs/44026136151), on PR #244: both native jobs passed the startup, UID and restart probe. At that run's database state, each selected summary reported zero findings. The [new scan on 21 November](https://github.com/Joaomagh/credpay/actions/runs/44954572482) changed the result to UNKNOWN 0, LOW 4, MEDIUM 6, HIGH 1, CRITICAL 0 on **each** native architecture. Both selected ZIP artifacts were downloaded into ignored `.local/security/postgres-candidate-review/` and their SHA-256 digests matched GitHub. [Run 44957409647](https://github.com/Joaomagh/credpay/actions/runs/44957409647) confirmed the new gate: report controls passed, the real HIGH made both scan jobs fail, and selected evidence was still uploaded. The candidate remains blocked until the package upgrade has passed native scans.

Promotion requires reviewing the actual AMD64/ARM64 inventories, handling any remaining CRITICAL/HIGH findings, full service tests, migration/restore from a fresh backup, Compose/Kubernetes recovery and an explicit release decision. Existing Bookworm volumes must never be mounted directly into this Alpine candidate for a test.
